# Incident 002 — Terraform Provider Binary Committed to Git History

**Date:** 2026-08-04  
**Severity:** Medium (blocked push, required history rewrite)  
**Status:** Resolved  

## Symptoms

`git push` to GitHub failed with:

```
remote: error: File terraform/.terraform/providers/registry.terraform.io/hashicorp/aws/5.100.0/linux_amd64/terraform-provider-aws_v5.100.0_x5 is 674.20 MB; this exceeds GitHub's file size limit of 100.00 MB
remote: error: GH001: Large files detected.
```

Push had already compressed and transmitted ~147 MB of objects before being rejected
by GitHub's pre-receive hook.

## Investigation

1. Checked `.gitignore` — it existed, but only inside `terraform/.gitignore`, not at
   the repository root
2. `git status` confirmed `terraform/.terraform/` (containing downloaded provider
   binaries) had been staged and committed in the initial commit
3. Attempted `git rm --cached` on the offending files and re-committed — push still
   failed with the same error
4. Root cause of the *second* failure: removing a file from the working tree and
   committing that removal does not remove it from git history. The 674 MB blob
   was still present in an earlier commit, and `git push` transmits full history,
   not just the current tree state

## Root Cause

Two compounding issues:

1. `.gitignore` was placed in `terraform/` instead of the repository root, so the
   first `git add .` run from the project root did not respect it and staged
   `terraform/.terraform/` along with the rest of the project
2. Once a large binary is committed, `git rm --cached` + new commit is
   insufficient — the blob remains reachable from history and is still pushed

## Fix

Full history reset rather than selective history rewriting (acceptable here since
the repository was brand new with no collaborators or existing remote history worth
preserving):

```bash
rm -rf .git
git init
git branch -M main
git remote add origin https://github.com/bahasaki/aws-event-driven-orders.git
```

`.gitignore` was moved to the repository root before the first real commit, covering:

```
terraform/.terraform/
terraform/.terraform.lock.hcl
terraform/terraform.tfstate
terraform/terraform.tfstate.backup
terraform/response.json
lambdas/*.zip
__pycache__/
*.pyc
```

## Verification

```bash
git add .
git status   # confirmed no .terraform/, no .zip, no .tfstate in staged files
git commit -m "feat: initial infrastructure - SNS, SQS, DLQ, Lambda pipeline"
git push -u origin main
# Total push size: 4.49 KiB, succeeded
```

## Prevention

- `.gitignore` must live at the repository root before the *first* `git add .`,
  not be added retroactively — ignore rules only prevent staging, they don't
  retroactively clean history
- For projects with a Terraform working directory, add `.terraform/` and
  `*.tfstate*` to root `.gitignore` as a standing first step, before running
  `terraform init`
- If a large binary is ever committed, resolve it before any collaborator pulls
  the branch — a full `rm -rf .git && git init` is only safe on a repo with no
  other contributors and no history worth keeping. On a shared repo, the correct
  tool would be `git filter-repo` or BFG Repo-Cleaner instead.

## Lessons Learned

1. `.gitignore` scope matters — a nested `.gitignore` only governs files under
   its own directory tree relative to where `git` resolves it from the run location  
2. Git history is additive — removing a file from the working tree does not shrink
   already-committed history; large files require history rewriting tools, not
   just a follow-up commit
3. Terraform provider binaries (`.terraform/providers/`) should never be committed —
   they are regenerated by `terraform init` and can be hundreds of MB per provider
